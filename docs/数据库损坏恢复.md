# 数据库损坏恢复指引

> 适用场景：PersonalMediaManager 启动失败，`tray-crash.log` 或弹窗里出现 **`database disk image is malformed`**、**`SQLITE_CORRUPT`**、**`file is not a database`** 等字样——SQLite 主库 `pmm.db` 真损坏。
>
> 先安心：本程序**默认每日 04:00 自动备份**（`pmm.db` + 密钥环），滚动保留最近 `Backup_RetainCount`（默认 7）份。绝大多数情况能从备份无损恢复。

---

## 〇、先判断是不是「真损坏」

启动期 `DatabaseStartupHealer` 会先做一次 `wal_checkpoint(TRUNCATE)` + `PRAGMA quick_check`，区分两种情况：

- **WAL 误报**（最常见，断电/强杀进程导致）→ 程序**自动修复并继续启动**，无需人工干预。
- **真损坏**（页损坏/磁盘坏道/外来 WAL 孤儿）→ `quick_check` 非 ok，程序原样抛出 → 落 `tray-crash.log` + 弹窗（即本文档场景）。

所以你能看到这份指引对应的崩溃，说明已是「真损坏」，按下面恢复。

**数据目录在哪？** 二选一（绿色软件优先前者）：

- 程序目录下的 `data\`（exe 旁，可写时优先）
- `%LocalAppData%\PersonalMediaManager\`（程序目录不可写时回退）

崩溃弹窗里会直接给出当前数据目录绝对路径；正常运行时也可在「设置 → 系统 → 数据目录」看到。下文记作 `<数据目录>`，其结构：

```
<数据目录>\
├─ pmm.db            ← 主库（损坏的就是它）
├─ pmm.db-wal        ← WAL（恢复时必须连它一起清，否则污染新库）
├─ pmm.db-shm        ← 共享内存索引（同上）
├─ keys\             ← DataProtection 密钥环（解密 TMDB/AI/PAT 等字段，必须随库一起恢复）
└─ backups\          ← 自动/手动备份 pmm-backup-*.zip（每份含 pmm.db + keys\）
```

---

## 一、方案 A（首选）：从备份恢复

### A-1 程序还能启动（少数情况：损坏不致命）

设置 → 系统 → **备份与恢复** → 选最近一份备份 → **恢复** → 按提示**完整退出托盘并重启**。恢复走「暂存 + 启动期换库」，旧库会自动备份为 `pmm.db.preimport-*`，密钥环立即合并。安全、可回退。

### A-2 程序无法启动（本文档主场景）——手动恢复

> ⚠ **关键陷阱：必须连 `pmm.db-wal` / `pmm.db-shm` 一起清掉。** 只换 `pmm.db` 而留下旧 WAL，旧 WAL 会在下次启动 checkpoint 时回写覆盖刚恢复的内容（「外来 WAL 孤儿」），表现为「恢复没作用、甚至再次损坏」。

1. **完整退出应用**（托盘 → 退出；确认进程已结束）。
2. 打开 `<数据目录>`。
3. 把 **`pmm.db`、`pmm.db-wal`、`pmm.db-shm` 三个文件一起**剪切到一个临时文件夹（先别删，留作方案 B 的 `.recover` 兜底）。
4. 进入 `<数据目录>\backups\`，找到**最新**的 `pmm-backup-*.zip`（文件名时间戳越大越新），解压：
   - 把里面的 **`pmm.db`** 复制进 `<数据目录>\`；
   - 把里面的 **`keys\` 下所有文件**复制进 `<数据目录>\keys\`（覆盖合并）。
     > 密钥环必须一起恢复，否则 TMDB ApiKey / AI Provider ApiKey / GitHub PAT 等加密字段在新根下**解不开**。
     > **版本兼容**：备份须出自与当前程序兼容的版本——0.1.0 迁移基线重置（2026-06-11）之前的旧备份不可用于新版（恢复后启动会因迁移历史不匹配而失败），此类备份只能放弃，按第四章删库重建。
5. 重启应用。

恢复后建议立刻「设置 → 系统 → 备份与恢复 → 立即备份」打一份新基线，并核对「设置 → 系统 → 最近备份」时间正常。

---

## 二、方案 B（无可用备份）：`sqlite3 .recover` 深度恢复

仅在 `backups\` 为空或全部不可用时使用。`.recover` 是**尽力而为**，可能丢失少量最新行，但能从损坏库里抢救出绝大部分数据。

1. 下载官方 `sqlite3.exe`（SQLite 官网 *Precompiled Binaries for Windows* 的 tools 包）。
2. **完整退出应用**。
3. 在临时文件夹里对**损坏副本**（方案 A-2 第 3 步挪出来的那份）操作，命令行：
   ```
   sqlite3 pmm.db ".recover" | sqlite3 pmm-recovered.db
   ```
4. 校验恢复结果（应输出 `ok`）：
   ```
   sqlite3 pmm-recovered.db "PRAGMA integrity_check;"
   ```
5. 用 `pmm-recovered.db` 替换 `<数据目录>\pmm.db`，并**确保 `<数据目录>` 下没有 `pmm.db-wal` / `pmm.db-shm` 残留**（有就删掉，避免外来 WAL 孤儿）。
6. 密钥环 `keys\` 维持现状即可（`.recover` 不动 keys；只要没换数据根，原 keys 仍能解密）。
7. 重启应用，立刻打一份新备份做基线。

---

## 三、预防（强烈建议）

- **确认自动备份开启**：设置 → 常规 → 备份，`启用` 打开，保留份数 ≥ 7。
- 重要操作（清空历史 / 重置配置 / 导入）前，先「立即备份」或「导出」。
- **迁移数据目录时整目录搬**：必须连 `keys\` 与 `backups\` 一起搬，否则加密字段在新根解不开（数据根漂移坑）。
- 不要在程序运行时手动拷贝/覆盖 `pmm.db`（WAL 模式下会损坏）；一切换库都走「完整退出 → 操作 → 重启」。

---

## 四、仍无法恢复？

- 留好损坏副本（方案 A-2 第 3 步挪出来的三件套）与 `tray-crash.log`，它们是定位根因的关键证据。
- 最坏情况：删除 `<数据目录>\pmm.db*` 三件套后重启，程序会自动重建空库并重种默认配置（**历史记录会丢失**，但配置可重填）；密钥环 `keys\` 保留即可继续用既有加密字段。
