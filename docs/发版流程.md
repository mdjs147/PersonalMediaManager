# 发版流程

> 与 [CLAUDE.md §9.3.2 / §9.5](../CLAUDE.md) 和 [.github/workflows/release.yml](../.github/workflows/release.yml) 对齐。

---

## 一、什么时候发版

| 触发条件 | 是否发版 |
|---|---|
| 修 bug / 改文案 / 内部重构 | ❌ 不发版，合 main 即可；下个发版窗口顺带带上 |
| 新 feature / 新 API / 新增 EF migration | ❌ 不发版，合 main 即可（次版本号在合 main 时已升） |
| 客户希望体验新版本 / 累计变更足够 / 修复了影响所有用户的 bug | ✅ 发版 |

**核心规则**：发版动作 = 打 tag。tag 与 `Directory.Build.props:PmmProductVersion` 严格 1:1 对应。

---

## 二、版本号联动

PMM 维护四套版本号（详见 [Directory.Build.props](../Directory.Build.props) 顶部注释）。**发版时要动的是哪一个，按下表查**：

| 字段 | 谁升 | 何时升 | 发版时是否动 |
|---|---|---|---|
| `PmmProductVersion` | **发版者** | **打 tag 前** | **必动** |
| `VersionPrefix` | 后端开发者 | 后端代码合 main 时（feature → main） | 已在合 main 时升，发版当下通常**不动** |
| `PmmDbVersion` | DB 改动作者 | 新增 EF migration 时 | 已在合 migration 时升，发版当下**不动** |
| `FrontendVersion` | 前端开发者 | 前端独立 `npm version patch/minor/major` | 已在前端日常迭代时升，发版当下**不动** |

> 0.x 阶段简化：MINOR 升前三套通常一起跳一档（如 0.1 → 0.2）；PATCH 单升 `PmmProductVersion` 即可。

## 三、发版操作清单（**复制粘贴照做**）

> 假设要发 **v0.1.0**，从一个干净的 main 分支开始（无未提交改动）。

### 3.1 升 `PmmProductVersion`

编辑 [Directory.Build.props](../Directory.Build.props)：

```xml
<PmmProductVersion>0.1.0</PmmProductVersion>
```

### 3.2 commit + 双推

```powershell
git add Directory.Build.props
git commit -m "release: bump PmmProductVersion to 0.1.0"
git push origin main   # 双推 Azure + GitHub
```

### 3.3 打 tag

```powershell
git tag -a v0.1.0 -m "v0.1.0"
git push origin v0.1.0   # tag 也双推 → Actions 在 GitHub 端被触发
```

> 注意 `tag -a`（annotated tag，含作者 + 时间 + 注释），不要用 lightweight tag `git tag v0.1.0`（无元数据，工具识别度差）。

### 3.4 看 Actions 跑

打开 [Actions 页](https://github.com/mdjs147/PersonalMediaManager/actions)，等 `release` workflow 跑完（约 5-8 分钟）。Steps 顺序：

1. ✓ Checkout
2. ✓ 解析 tag 与版本号
3. ✓ 校验 `PmmProductVersion` 与 tag 一致 ← 若失败说明 §3.1 忘改
4. ✓ 装 .NET 10 SDK + Node 22
5. ✓ 前端 npm ci（vite build 随 dotnet publish 自动触发）
6. ✓ dotnet publish Launcher 单文件 self-contained win-x64（前端 + appsettings 嵌入）
7. ✓ 产物校验（确为单一 exe）+ 重命名为带版本号 exe（不打 zip）
8. ✓ gh release create + upload

### 3.5 看 Release

打开 [Releases 页](https://github.com/mdjs147/PersonalMediaManager/releases)，确认：

- 有 `v0.1.0` Release
- Assets 列表里有 `PersonalMediaManager-0.1.0-win-x64.exe`（单文件，约 100-200 MB）
- Release notes 自动生成（GitHub 从上次 Release 起的 commit 摘要）

如果是预发布需要编辑标题 / 描述 / 改 Draft → Published，在 Release 页右上「Edit」即可。

### 3.6 验证客户端能拉到

```powershell
# 模拟客户端的「检查更新」调用
# 勿用裸 `curl`：Windows PowerShell 5.1 里 curl 是 Invoke-WebRequest 的别名，`-s` / `-H` 会报参数错误；
# 要用原生 curl 须显式写 `curl.exe`。下面是等价的纯 PowerShell 写法（5.1 / 7+ 通用）：
Invoke-RestMethod `
  -Headers @{ 'User-Agent' = 'PersonalMediaManager/0.1.0' } `
  -Uri 'https://api.github.com/repos/mdjs147/PersonalMediaManager/releases/latest' |
  Select-Object tag_name, name, published_at, html_url
```

预期输出：
```
tag_name : v0.1.0
name     : v0.1.0
...
```

正在跑的旧版 PMM 在最长 `Update:CheckIntervalHours`（默认 24h）后会自动发现。**想立刻测**：在 WebUI 设置 → 软件更新 页点「立即检查」。

## 四、失败回滚

### 4.1 Workflow 跑失败（最常见：tag 与 PmmProductVersion 不一致）

```powershell
# 1. 删本地 + 远端 tag
git tag -d v0.1.0
git push origin :refs/tags/v0.1.0

# 2. 修 Directory.Build.props（或 yml）
# ...

# 3. commit 修正 + 重新打 tag
git add -A
git commit -m "fix release issue"
git push origin main
git tag -a v0.1.0 -m "v0.1.0"
git push origin v0.1.0
```

### 4.2 Release 已创建但 exe 产物错误（少见）

GitHub 网页删 Release（保留 tag）→ workflow 重跑（**人工**触发：到 Actions 页点 Re-run，或推个新 tag）。

或者：

```powershell
# 删 Release + 删 tag 同时来
gh release delete v0.1.0 --yes
git push origin :refs/tags/v0.1.0
git tag -d v0.1.0

# 修代码 → 重打 tag
```

### 4.3 PmmProductVersion 已升但暂不想发版

直接 commit 把 `PmmProductVersion` 改回去 + push main。**不要打 tag** workflow 就不会跑。

## 五、平台支持路线

当前 release.yml **仅打 win-x64 单 exe**。**macOS 支持已移除**（2026-06-11 决策，产品仅支持 Windows，macOS 不在路线图），原「macOS 先发 Host 服务包」扩展路径已删除。仅剩一条占位扩展路径（按用户需求触发）：

### 5.1 Linux 服务版（无托盘，纯 systemd 模式）

- `runs-on: ubuntu-latest`
- `dotnet publish src/PersonalMediaManager.Host -r linux-x64 --self-contained true`
- 上传 `PersonalMediaManager-Host-{ver}-linux-x64.tar.gz`
- 附 `systemd/.service` 模板（待 Host 项目支持系统服务模式）

Linux 服务版目前仅是占位规划，**发版矩阵仅 win-x64**。

## 六、安全与合规

### 6.1 GITHUB_TOKEN 权限

`release.yml` 顶部声明 `permissions: contents: write` —— 让 `GITHUB_TOKEN` 能写 Releases。**不需要 PAT**（GitHub Actions 自动注入一次性 token，run 结束即失效）。

### 6.2 客户端「检查更新」用的 PAT 与发版无关

详见 [CLAUDE.md §9.5 PAT 红线](../CLAUDE.md)：那个 PAT 是**终端用户为自己 PMM 实例配置**的、用于客户端**读** Releases API；发版动作用的是 Actions 自带的 GITHUB_TOKEN（写权限），两者完全独立。

### 6.3 不要把任何凭据写进 workflow

`release.yml` 里所有凭据都走 `${{ secrets.* }}`，**不允许** hardcode 任何 token / API key。当前仅用了 `GITHUB_TOKEN`（GitHub 自动注入，不需要在 Secrets 配）。
