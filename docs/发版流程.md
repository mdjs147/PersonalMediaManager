# 发版流程

> 与 [CLAUDE.md §9.3.2 / §9.6](../CLAUDE.md) 和 [.github/workflows/release.yml](../.github/workflows/release.yml) 对齐。当前源码目标为产品 **0.5.0**；修改源码版本不表示已经发布或部署。

## 一、版本来源与发布边界

PMM 只人工维护根 [Directory.Build.props](../Directory.Build.props) 的 `PmmProductVersion`，格式固定为 `X.Y.Z`。后端、前端、WebUI、托盘、API、更新检查与发布包采用同一产品版本。`VersionPrefix` 自动派生；前端 `package.json` 和 `package-lock.json` 中的项目版本由脚本同步，不再单独执行 `npm version`。

数据库只追踪 EF migration ID、已应用 / 待迁移集合与状态，不再发布独立 schema SemVer。旧 `db/version-map.json`、已发布 CHANGELOG 和已有迁移文件保留为历史记录。`__EFMigrationsHistory.ProductVersion` 是 EF 工具版本，不是 PMM 产品版本。

现有 Release workflow 同时监听 `main` 和 `v*` tag：

| 触发 | 工作流行为 |
|---|---|
| 推送 `vX.Y.Z` tag | 校验 tag 与 `PmmProductVersion` 完全一致，再创建 / 复用 Release 并上传单文件 exe |
| main 中的产品版本尚无对应 tag | 自动为当前提交创建 tag 与 Release，上传正式 exe |
| main 中的产品版本 tag 已指向当前提交 | 按正式发版重跑，恢复可能失败的资产上传 |
| main 中的产品版本 tag 已指向其他提交 | 只生成保留 7 天的开发 Artifact，不改变正式 Release |

**新产品版本进入 main 会触发发布。** 在该合并 / 推送前须取得发布授权；不能把“只合并、不打 tag”当成暂停发布的方法。普通开发期间沿用既定产品版本，不因每次后端、前端或数据库改动分别升号。具体产品版本按已确定的发布范围选择，不因“主版本号”一词擅自跳 SemVer 的 major 位。

## 二、只修改一次版本

以本轮目标 `0.5.0` 为例，只编辑：

```xml
<PmmProductVersion>0.5.0</PmmProductVersion>
```

然后在仓库根运行：

```sh
npm --prefix src/PersonalMediaManager.Frontend run version:sync
npm --prefix src/PersonalMediaManager.Frontend run version:check
```

`version:sync` 自动更新前端两个清单的项目版本；检查生成 diff 并随产品版本修改一起提交。`version:check` 不写文件，也不依赖已安装的 npm 包；任一派生值漂移或源版本无效即失败。GitHub PR / Release、Azure CI 和本地打包脚本都在安装依赖或构建前执行该检查，避免自动同步掩盖未提交的漂移。

.NET `AssemblyVersion` / `FileVersion` 固定由产品版本加 `.0` 派生（本轮为 `0.5.0.0`），不附加提交计数。`InformationalVersion` 的 `+commit[.dirty]` 元数据和构建时间仅用于识别具体产物，不构成独立产品版本。

## 三、合并、发布与部署核对

- [ ] 核对唯一产品版本及待发布 commit，确认本次发布范围已冻结
- [ ] 同步前端兼容元数据并通过 `version:check`，检查程序集、WebUI、托盘和 API 均来自同一产品版本源
- [ ] 核对本次是否新增 EF migration；部署时读取目标环境的已应用 / 待迁移集合，确认没有未知迁移或迁移历史缺口
- [ ] 完成当前代码的适用回归与目标平台验证；构建成功不能代替模型效果或运行验收
- [ ] 确认发布授权覆盖新版本进入 main 的自动 Release；暂停发布或等待评测时保持暂停
- [ ] Release 成功后核对 tag、Release、产物文件名、内部版本与 commit 一致，保存工作流和验证证据
- [ ] 部署前确认部署授权及运行前置条件；部署后从实际服务、UI 与迁移状态再次核验，源码或构建结果不代表部署成功

报告一个产品版本、commit、迁移状态与验证结果即可，不再要求四套版本的旧、新值报告。没有新增 migration 时明确记录“无新增迁移”；迁移检查失败时报告失败，不推断数据库已是最新。

## 四、发布操作

### 4.1 准备变更与合并

在开发分支完成版本源和自动同步元数据的修改，通过核对与回归，再按仓库 PR / 合并流程推进。确认发布授权后合入并推送 main；公开工作区的 origin 指向 GitHub。若需要内网镜像，使用独立 Azure remote 显式同步，不配置隐式双推。

新版本 tag 不存在时，本次 main 工作流会自动创建。若使用手动 tag 路径，须先确认目标 commit 中 `PmmProductVersion` 正确且没有同名 tag，再按授权创建 annotated tag 并推送；不要在 main 自动发版进行中重复创建同名 tag。

### 4.2 验证 Actions 与 Release

打开 [Actions](https://github.com/mdjs147/PersonalMediaManager/actions)，核对 `release` 工作流的目标提交及以下结果：

1. 解析 ref、产品版本和正式发版 / 开发构建分流
2. 正式发版时校验 tag 与 `PmmProductVersion` 一致
3. 安装 .NET 10 SDK 与 Node 22，执行只读 `version:check` 后再 `npm ci`
4. 发布 Launcher 单文件 self-contained win-x64；前端与 appsettings 随 publish 嵌入
5. 校验产物恰为单一 exe，命名为 `PersonalMediaManager-0.5.0-win-x64.exe`
6. 创建 / 复用 `v0.5.0` Release 并上传产物；开发构建仅上传 Artifact

到 [Releases](https://github.com/mdjs147/PersonalMediaManager/releases) 确认 tag 与资产完整。自动工作流创建正式 Release，不能把它当成待审核的 Draft；GitHub 自动生成的说明还须检查是否准确反映发布范围。

### 4.3 验证客户端升级检查

客户端通过 `IVersionInfoProvider.GetStatic().Product` 取得当前产品版本，并与 GitHub `/releases/latest` 的 tag 去掉 `v` 后按 SemVer 比较，不使用前端 npm 清单或独立后端版本。

```powershell
Invoke-RestMethod `
  -Headers @{ 'User-Agent' = 'PersonalMediaManager/0.5.0' } `
  -Uri 'https://api.github.com/repos/mdjs147/PersonalMediaManager/releases/latest' |
  Select-Object tag_name, name, published_at, html_url
```

若本轮已发布且仍是 latest，预期 tag 为 `v0.5.0`。旧版 PMM 会在下一次更新检查时发现；可在 WebUI 设置 → 软件更新点击「立即检查」。更新检查只提示新版及下载链接，不自动替换已运行的程序。

## 五、失败处理与暂缓

### 5.1 版本校验失败

若 `version:check` 失败，核对唯一源 `PmmProductVersion`，运行 `version:sync` 并审查生成 diff，再提交修正。不要分别手工修改多个版本值，也不要靠构建时自动同步跳过 CI 检查。

若 tag 与产品版本不一致，先核对 tag 所指提交和发布意图。不得直接覆盖已发布版本来掩盖错误；选择修正提交和新的产品版本，或在明确授权的未发布 tag 修复流程中处理。

### 5.2 上传失败或产物错误

目标 commit 未变、只是工作流或上传临时失败时，可重跑同一发版提交的 Actions。现有工作流复用 Release，并以 `--clobber` 恢复资产上传。若要修改源码或替换已公开产物，先确认影响和授权；不能把新提交伪装成原发版提交。

### 5.3 版本已写入但暂不发布

在开发分支保留目标版本和待发布状态，不把这个尚无 tag 的新产品版本推入 main。因为 main 新版本会自动发版，“不手动打 tag”不能阻止发布。部署是另一个动作，发布成功也不能替代部署授权与部署后验证。

## 六、平台与凭据边界

当前 `release.yml` 正式发布 **win-x64 单 exe**，没有独立安装器版本。Linux Server 与 macOS 原生菜单栏的本地构建、验证和现阶段限制见 [跨平台运行](跨平台运行.md)；它们已在源码与 PR 验证流程内，但当前不随 Release workflow 自动公开发布可移植包。

GitHub Actions 使用自动注入的 `GITHUB_TOKEN`，权限为本仓 `contents: write`，不需要用户 PAT。客户端可选的升级检查 PAT 仅用于读取 Releases API，按 [CLAUDE.md §9.5](../CLAUDE.md) 加密保存。二者不得混用，不把任何凭据写入 workflow、脚本或 tracked 配置。
